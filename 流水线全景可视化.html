全景总览：一条主线，两处人工门

官方主线（README）：/prd → /pd-review → 现状查证 → /tech-spec → /issue-split → 门② → 逐票 /implement → freeze → /ai-review → 复跑+conformance → promote → finalize → /review

整条流水线的核心设计：人只出现在两个固定位置——门②（拆票清单人审）与最终 merge-main 确认；其余所有异常收敛为 human-decision 决策包，由主会话单点问人。段与段之间靠 frontmatter 状态机衔接（待写PRD → 定稿 → 已确认（待拆解）→ confirmed → merged → done），每一环不满足门禁就停，不降级跳过。

需求段：怎么把「一句话想法」逼成「完整需求」

/pd-plan → /prd → /pd-review（横切：/prototype）

需求段的质量不靠「写得认真」，靠三台机器：拷打轮次（用决策树保证问题问完）、行为契约（FR 必须可观察、可测试）、修订式评审（pd-review 发现缺口直接改文档而不是提建议）。三者首尾相接，缺什么当场补进文档。

0

/pd-plan读上下文与模块归属

按固定顺序读：GLOSSARY → 最新 project memo → EXPERIENCE「需求阶段经验」节 → 已绑定 feature brief → 已绑定 PRD → pd-review-report。命中经验规则的坑直接进缺口清单，不重复问。新需求先确认 feature-module 归属（用户最终确认后才建目录，禁止「杂项」模块，粒度预算 4–10 个）。

自动化产物：上下文总结
1

/pd-plan先判断需求意义，再谈方案

解决什么问题、谁受影响、为什么现在值得做、不做的代价、做完的成功标准——这五问没说清之前，不进入方案设计。同时判定阶段模式：MVP（初期验证）/ STABILITY（成熟链路，优先边界与回退）/ DECOMPOSE（大需求先拆）/ COMPLETE（小需求防碎片化）。

默认「必须问」：意义是否成立 / 模式是否选错 / 方案是否误导实现
2

/pd-plan拷打轮次：把需求当决策树走完

每轮把 frontier（前提已定、现在就能问）上的问题一次问完，每题给推荐答案；回答后 frontier 外推、重算，进入下一轮。未决问题强制三归类：可假设继续（写出假设）/ 必须提问后继续（不许绕过）/ 仅记录为风险。

  • 事实自查：代码/文档/环境查得到的（现有字段、入口、指标现状）自己 Read/Grep，不问用户；
  • 不可拷打出口：同一问题追两轮仍抽象、答案依赖「看到实物」→ 标记「待确认（需原型）」，交给 /prototype，拿到 verdict 后以一行答案回流继续拷打；
  • 终止条件：frontier 为空 且 11 个覆盖维度每一项都有归属——不允许静默跳过。
11 覆盖维度：需求意义 / 目标用户 / 触发时机 / 范围边界 / 主流程 / 异常与边界 / 状态流转 / 权限差异 / 数据口径 / 成功与验收标准 / 依赖与风险——每项标「已确认 / 假设 / 待确认」。
人工：回答问题循环至 frontier 空/prototype verdict 回流
3

/pd-plan共识确认 → Feature Brief

先输出共识摘要（关键决策清单 + 维度归属，用「都谈拢的 / 先按假设走的 / 还没定的」分组说人话）+ 产品逻辑结构图（节点 ≤12、边 ≤20，假设/待确认画虚线，Mermaid 源码落盘）。用户确认后才产出 Feature Brief（frontmatter status: 待写PRD / 待验证 / 不进入）；推翻任一条则回到对应分支继续拷打。

人工：共识确认产物：feature-brief-*.md/prd 以 status=待写PRD 为开工门禁
4

/prd把 brief 转成技术友好的行为契约

开工门禁：brief 存在且 status=待写PRD，brief 里的「待确认」未闭环的不得写入正式要求。按 14 章固定骨架写，每模块写齐：功能目标 / 前置条件 / 用户操作 / FR / 业务规则 / 状态迁移表 / 异常边界 / 权限矩阵（角色×操作×允许拒绝×拒绝反馈）/ 字段级输入输出表（空值语义、枚举全列）/ 判定口径（公式、单位、精度、舍入、时区、窗口）。

自动化产物：prd-*.md（status: 草稿）
5

/pd-review修订式评审：低于 8 分直接改，不是提建议

7 个维度 0–10 分评分：目标完整 / 范围完整 / 规则完整（判定分支含边界值、FR 单一可观察行为）/ 状态·异常完整（迁移表、空值语义、枚举、权限矩阵）/ 交接就绪（不依赖口头补充）/ 验收就绪（指标与事件可执行）/ 术语口径一致。每一个低于 8 分的维度，当场修改 PRD 补到当前结构。评审重点还包括「是否把关键决策错误地下放给实现阶段」；三个行为覆盖抽检（字段 / 状态 / SM 埋点）答不出的，对应维度不得高于 7 分。

结论三档：可交付 / 可交付但有风险 / 阻塞。修订完成且非阻塞 → PRD 置 status: 定稿（FR 编号自此「不复用、不重排」），报告 verdict 成为 /tech-spec 的开工门禁字段。

verdict≠阻塞 才能进 /tech-spec产物：PRD 定稿版 + pd-review-report

FR 规则：一条 = 一个可观察行为

  • EARS 句式，全局编号 FR-<模块号>-<序号>，复合行为必须拆条；
  • 每个用户操作步骤至少被一条 FR 覆盖，硬性要求一律写成 FR；
  • 每条 FR 至少带一条可测试后果——写不出的降级移入「待确认问题」，不允许伪装成需求。

输出前 10 条自检清单

  • 无边界表述检查（禁「体验更好」「后续再细化」）；
  • 成功度量必须承接、假设（AS 编号）与阻塞项分置；
  • 一级章节不可删（无内容写「本次无」）；
  • 三个行为覆盖抽检：字段 / 状态 / SM 埋点各抽一条对得回 FR；
  • AC 编号稳定，可被技术方案逐条引用。

术语与口径强一致

读文档先读 GLOSSARY；指标必须带口径（定义 / 窗口 / 来源）；用法与表内定义冲突时先裁决再写；讨论中确定的新术语立即回写，淘汰说法记入「拒绝词」防回潮。

/prototype：不可拷打问题的专用出口

识别信号：两轮追问仍只有抽象回答，或答案本质依赖「看到、点到实物」。一个原型只回答一个问题（LOGIC 规则类 / UI 多变体类），用户上手裁决后落 verdict；其中「决策性片段」（状态机 / reducer / schema）是 tech-spec 3.5 节唯一允许内联的代码来源。

文档写作纪律

每句话可验证、有判断标准；关键规则当场裁决，不留「开发时再决定」；假设写成可见条目，不藏在叙述里；tradeoff 必须写明选择、放弃项与原因。

需求段防的坑

  • 漏维度 → 11 维清单逐项归属，不许静默跳过；
  • 需求悬空 → FR 必须可测试，否则降级；
  • 评审走过场 → 低分维度直接改文档，答案不了抽检就压分；
  • 歧义扩散到开发 → GLOSSARY 口径先裁决，拒绝词防回潮。
③

开发计划段：怎么让方案与拆票高质量

/setup-dev → /how /why 现状查证 → /tech-spec → /issue-split → 门②

计划段的高质量来自三层保证：现状真实（How/Why 查证，不凭记忆写方案）、结构机器可校验（3.1 文档树是机器契约，树↔票 scope 闭合检查）、拆票有硬红线（文件数 / LOC / scope 可枚举性是确定性数字，不是感觉）。

1

/tech-spec · Step 1How 现状建模 + Why 历史约束

现状查证必做——先搞清系统现在真实怎么运转；Why 按决策相关性触发——查清历史动机防止「顺手推翻过去的教训」。轻量证据直接写进 spec 2.1 证据表；复杂或可复用的调查才归档 research/。

自动化（按需升级深度）产物：2.1 How/Why 证据表
2

/tech-spec · Step 2候选方案综合，不拍脑袋

承重决策（公共接口、ownership、持久化、并发共享状态、技术选型）每项至少 2 个结构不同的候选 + 3–6 条评分准则，综合结果落 3.6 DEC-ID 表；公共接口 usage-first 先写调用方怎么用；旧实现清理属方案范围（不留兼容层）。

每项承重决策可追溯 DEC-ID
3

/tech-spec · Step 3–4技术拷打 → 共识 → 落盘

技术决策同样按拷打轮次制，frontier 未清空前不输出完整方案。共识确认后产出两份产物：

  • <feature-summary>-tech-spec-*.md（status: 已确认（待拆解） = /issue-split 的开工门禁）；
  • acceptance-plan.yaml（测试计划，详见 ④ 节）。
人工：共识确认产物：tech-spec + acceptance-plan
4

/issue-split垂直切片拆票（tracer bullet）

每票纵向切穿所有层、独立可演示；首张票是最细的端到端贯通；票间阻塞关系构成 DAG；宽改造按 expand–contract 拆。每票写可自动判定的 DoD：1–3 条「命令 + 期望退出码（+ 可选期望输出）」；bug 票 DoD 必含复现回归测试命令。DoD 覆盖性自查产出「需求点 → 票 / DoD」覆盖表，防漏防重。

DoD 会被 verify_issue.py 逐条真实执行
5

门②唯一例行人工确认点

先跑两道只读机器检查（validate-plan + check-plan，有规则变更再加 arch_check.py validate），全过才向用户呈现：编号票清单 + 覆盖表 + 验收分工摘要（AI 完整验收 / AI 执行人工复核 / 纯人工各几条）+ DAG 依赖顺序。确认后 proposed → confirmed，此后标题 / DoD / declared-scope / 方案切片不得单方面修改。

人工：唯一的拆票确认机器检查先于人审

3.1 模块拆解文档树：机器契约（spec-tree-version: 1）

  • 树形列出将改动的每个文件：路径 + 动作（新增/修改/退役）+ 一句计划变动逻辑；禁 glob、禁绝对路径、缺说明即拒收；
  • 树↔scope 闭合检查（check-plan，门②前强制）：树文件无人认领（漏拆）、票 scope 路径不在树中（扩围）、glob 零命中、切片与重算投影不一致——任一命中直接拦门②；
  • 每票定稿后由 spec_tree.py slice 确定性生成「方案切片」（按 SHA256 校验来源），scope 修订必须重新生成，不得手改。

3.2 架构影响：规则变更有唯一通道

  • 总览 11 节 + 层/组动作表（new | modify | retire），写入唯一真源 docs/ARCH-CHECK.json 后 render write 生成 ARCHITECTURE.md（禁手改）；
  • 规则变更（新增 / 删除 / 放宽 / 改阈值）必须写进 3.2 + 承接票 declared-scope；ai-review 把「删除/放宽规则」当高风险项审查；
  • 票级不设架构门——架构检查只在 feature candidate 的 freeze/check 强制跑，pre-push 只做预警。
粒度红线：确定性数字，不是感觉 预计生产代码 文件数 > 10、LOC > 400，或 scope 不可枚举（只能写出目录级 glob）→ 本票必须再拆；单票横跨 > 2 个模块 → 自动再拆或标记人工裁决。粒度取向取少不取多，红线是上限不是目标；任何额外的测试都不能豁免红线。实现期 changed path 越界直接 FAIL。
为什么开发计划能高质量 ① 追溯分层：FR 定义可观察行为 → 规则表定义分支/计算/权限 → spec 定义实现与决策 → 票定义交付边界与 DoD → 验收计划定义完整可执行 case，下游用稳定 ID + 来源引用承接，不重写上游；② 机器契约：3.1 树让「计划改动面」从散文变成可校验数据，漏拆/扩围/越界全部脚本拦下；③ 决策留痕：承重决策双候选+评分准则，被实现证伪时走 redesign 换代（supersedes），而不是在旧文档上悄悄改口径；④ 确认前置：所有机器检查跑在门②之前，人只看检查过、核对过的清单。
④

测试计划与验证体系：怎么做到「计划可执行、结果可信」

acceptance-plan.yaml 双轴 AC · 四层验证 · TDD 见红强制 · 防伪造证据

测试计划不是开发完再补的文档，而是 tech-spec 阶段的确定性产物（每 campaign 一份 YAML），从 PRD 的 AC 场景逐条演化而来；执行时逐层收紧：票级内环 → 候选复跑 → 需求级 AC → CI full。

双轴验收矩阵：谁执行 × 谁判定

每条 AC case 声明两个独立维度：

  • executor：command / browser-agent / human——谁来跑、采集证据；
  • oracle：auto / auto+human-review / human——谁做最终判定。

浏览器操作不能替代人的业务判断；纯人工必须写 human_reason（固定六词表：intent / visual-ux / domain-judgment / high-risk / no-reliable-oracle / environment-unavailable）。

case 结构：每条都可执行

  • source：来源文档 + anchor（锚到 PRD/CR 具体位置）；
  • preconditions：环境 / 初始状态 / 测试数据；
  • steps：操作 + 输入 + 每步预期；
  • expected：最终量化结果 + assertions / human_expect；
  • documents：用 path + SHA256 绑定真实 PRD / change-request——上游变了计划立即失配，不能悄悄换源。

阈值纪律

所有阈值必须来自 PRD / change-request / 已确认决策，不得编造；验收收口只能向更严方向调整，降低人工要求必须回技术方案修订计划。整案通过的判定：全部 required case 自动 + 人工标准满足且证据齐备。

门②呈现验收分工

拆票确认时同时呈现：AI 完整验收几条、AI 执行人工复核几条、纯人工验收几条——人在门②就能看到「验收自动化率」，而不是等收口才发现一堆要手测。

四层验证体系（当前实现，已废除旧 light/scoped/full 档位）

层级跑什么在哪跑失败怎么办
1 · 票级内环 TDD 见红 + 本票 DoD + fast 套件（verify_issue.py run implementer）——每轮回修只重跑本票 DoD + fast，完整套件不冒充 CI full 票 worktree 自修复 ≤ max-fix-rounds，达上限 human-decision，「停止，不硬磨」
2 · 候选复跑 freeze 后 verify_issue.py run-candidate：对每票冻结的 DoD + fast 原样复跑一次，防「过期证据」 集成 worktree 任一失败阻塞收口
3 · 需求级 AC scoped_select.py 关联选择集（direct 全跑、indirect 跑到预算停）+ acceptance-plan 的 command / browser-agent AC 真实执行 + generation 证据 本机候选环境 漏项 / 重复 / 额外 AC 都会被 check --phase verify 抓出
4 · CI full full 只有 CI 一个入口（含 daily regression）；本机、票 worktree、监督循环一律不得跑 full；CI 不可用时保持「未验证」状态，不降级本机补跑 远端 CI main push 后 CI full 是安全网

TDD 见红不是口头声明

  • 写实现前先跑 verify_issue.py red，必须产生指向预期行为差异的断言失败——语法错误、导入错误、运行崩溃、或「首次就通过」均无效，重写后再跑；
  • 新增测试必须登记并由 runner 留见红证据；既有测试修改必须映射真实 DoD / tech-spec 行为变化，无映射、删测试、放宽无关断言 → 停止；
  • bug 票 revert 闭环：bug-regression 三段缺一不可——修复后绿 → 在一次性 detached worktree revert 生产修复必须见红 → 恢复后绿。专防「测试本来就会过」的假回归。

证据防伪造：只认机器链路

  • process_check.py --phase ticket 的 evidence 只接受 verification JSON + 哈希 raw log；Markdown 只是 JSON 的确定性渲染，手写 all-passed 不算数；
  • 没有 runner JSON、真实日志和精确候选绑定，不得宣称完成或 CI full 通过；
  • 生成物核对：在独立临时工作区重跑生成器并比较 tree，「只改了个字段」的文字声明无效；
  • 不接受手写测试通过、commit 前缀复用、同会话自评或本地 CI 自证。
为什么测试计划能高质量 ① 前置产出：计划在 tech-spec 阶段就成形，拆票时校验、实现时执行、收口时复跑——同一份计划贯穿三段，没有「实现完再想怎么测」的空窗；② 双轴分工：executor 与 oracle 分离，把「谁来跑」和「谁说了算」拆开，自动化率显式化、人工项逐条给理由；③ 逐层收紧：票级快（DoD+fast）、候选严（复跑+conformance）、CI 兜底（full+daily），质量门集中在该集中的位置；④ 证据可回放：每条结论都能对回 JSON 与哈希，「说测过了」不等于「测过了」。
⑤

自动化执行：怎么在「少问人」和「不失控」之间闭环

主会话监督循环 · /implement 票级内环 · human-decision · 无人值守熔断 · /ai-review

门②之后进入全自动段：主会话按 DAG 逐票派发 /implement，实现会话在独立 worktree 里完成「冻结→TDD→门禁→回报」，主会话复核后合入集成分支；普通过程无人工检查点，只有五类事件会停下来找人。

1

/implement启动校验：不过就不动代码

配置校验（agents/dispatch config + 角色解析）→ 只接受 confirmed 票 → blocked-by 全部 merged → 读票全文、tech-spec、PRD、GLOSSARY、ARCHITECTURE、EXPERIENCE「开发阶段经验」（已知坑开工前带回）。

状态/依赖机器判定经验回流点
2

delivery.py start冻结上下文，一票一 worktree

创建票分支（feat/<module>/<feature>/<campaign>-<issue-id>）与 worktree，dev/ 软链回主工作区；冻结 target / base / HEAD / tree / scope / 票 / DoD / spec / config 哈希到 ticket-context.json——开工后一切对照冻结值，漂移即停。

哈希冻结 · ticket-context v3
3

票级内环：TDD 实现 + 自修复

每次改动前后检查：deny 路径命中即停、测试修改必须映射 DoD、派生物只由生成器产生、每轮对照冻结 declared-scope、超 10 文件 / 400 LOC 即停 re-split。然后 TDD：red（行为断言失败）→ 写实现到绿（替代即删除，不留旧实现）→ 自修复轮 ≤ 上限，达上限保存轨迹返回 human-decision，不硬磨。

内环循环：写测试 → 见红 → 实现 → 重跑本票 DoD + fast →（失败）自修复 → 重跑……成功标准只认真实 runner 证据。承重决策被证伪 → operation=redesign 退回 proposed，回 /tech-spec 换代。
自动化内环循环
4

票级门禁 + 结构化回报

process_check.py --phase ticket 只读聚合：context/scope/deny、票粒度、见红与测试修改映射、生成物、dev 软链、预算、manifest、bug regression、活动 decision、implementer verification。全过 → 回报主会话；实现会话不自行 merge、不问人。

process_check证据：verification JSON + 哈希日志
5

主会话监督循环：合并与打回

每轮先 progress.py reconcile 只读对账，再按 DAG 派发下一票；delivery.py merge 复核「target 未前进 + 票级门禁 + implementer 证据 + 无活动 decision」后 no-ff 合入集成分支。失败票：verify-fails +1 并写 verify-fail，未达 2 次退回实现会话，达 2 次创建 human-decision，不再自动打回。

自动化merge 复核
6

全部票 merged → freeze → /ai-review 整需求评审

feature_closeout.py freeze 绑定 candidate / tree / 票组 / 计划哈希；独立实例（session/agent 不得与任何 implementer 相同）评审 review_base..candidate 全量 diff：先反向枚举需求（不看覆盖矩阵独立列行为点）再核代码；preview 中每个文件必须 reviewed 或 skipped（带原因），不得静默遗漏。检查维度：需求覆盖（跨票拼出完整主/失败路径）、架构一致性、接口契约、规则无 error 且删/宽有依据、测试映射、生成物洁净、旧实现残留（双路径 = high）、测试质量。

结论 pass / pass-with-notes / blocked；BLOCKER（critical/high）→ 开修复票走内环 → 重新 freeze → 新 candidate 必须重新评审，receipt round 递增，旧 receipt / 复跑 / conformance / 人工确认全部失效。

独立性 + receipt 哈希链blocked → 修复票 → 重新冻结评审
7

候选复跑 + conformance + AC 执行 + 报告

run-candidate 逐票复跑冻结 DoD；conformance：先反向枚举需求，再按 tech-spec 全节 + 全部票覆盖矩阵并集逐条核对（评审与符合性两次独立判断各自保留，不共享「通过」结论）；候选环境跑需求级 AC（command / browser-agent 真实执行 + 截图与 console 证据）；report 生成 acceptance-report，check --phase verify --record 核 receipt / 复跑 / conformance / AC 漏项重复 / 证据环境。

机器门禁聚合
8

人工最终验收 → promote → finalize

展示实际通过 / 失败 / 未验证 / 待人工原因；人明确给出 merge-main 原话 + 时间 + 候选 tree + 无附加条件，写入 confirmation.md 后重新 report——沉默、取消、超时都不算确认。随后 delivery.py promote 在同一授权进程内复核 receipt / 复跑 / conformance / 报告 / 确认哈希再合 main；finalize 逐票 close-and-clean、清理 integration worktree，任何一步失败保持 needs-attention，不用总结掩盖残留。push / Prod / rollback 永远需要另行授权。

人工：merge-main 确认promote 复核
9

/review复盘与经验回流

全部票 done + 人确认发布后：重建过程全景（时间线、自修复轮次、评审 round、验证统计、逃逸缺陷、规则巡检）→ 经验分级沉淀到两级库（项目级 EXPERIENCE.md / 通用级 ~/.pd-workflow/general-experience.md）→ 落盘 retro 报告。规则级先判：根治靠改流水线规则的（模板缺章节、阈值失准）不进经验库，写「流水线改进建议」。库操作四件套：去重（阶段+场景+语义）、晋升（项目→通用）、引入（通用→项目）、退役（触发场景消失即删）。下一个 feature 的 /pd-plan、/prd、/tech-spec、/implement 前置读取自动回流——飞轮闭合。

产物：retro + EXPERIENCE 更新回流下个需求

human-decision：唯一的问人通道

  • 分工：子会话只构造决策请求（不能问人、不能写包）；主会话是唯一写者，统一呈现、记录、路由；
  • 决策包：唯一真源 decisions/<id>.json；basis 三哈希（票/HEAD/报告）回答时必须一致，变了必须 supersede；2–4 个互斥选项各带受控 route；证据 ≤12 条带哈希摘要；
  • 路由词表：continue（resume/redispatch）/ supervisor（reconcile-routing、re-split、request-review、collect-evidence）/ defer / cancel——禁止 shell/命令字段、路径逃逸、秘密；
  • 状态机：pending → waiting → answered → routing → resolved；取消/超时=尚未回答，不等于选了推荐项；同票最多一个活动包；宿主 ack 持久化后才许解除 needs-human。

无人值守：熔断策略

  • 授权前置：unattended.md 写明可自主事项 / 禁止事项 / 预算 / 停止条件，人过目后开跑；合 main、Prod、push 永不因它获得授权；
  • 默认串行：同项目只跑一个循环，授权明确才允许 parallel-max；
  • 不问人：越界问题只建 human-decision 包保持 needs-human，继续其他无依赖票，不调用提问组件、不干等；
  • 熔断即停：额度达阈值（默认 80%）/ 耗尽 / 持续限流 / 鉴权失败 / 连续 2 次心跳无实质推进 → 立即停止派发与合并、写 circuit-break、撤销心跳、不自动 retry；
  • 心跳从紧：定时唤醒间隔 ≥2 小时且上一轮须有实质进展；续跑另起新会话，不反复唤醒同一长会话；
  • 停止条件：frontier 空 + 全票 merged/done + finalize，或剩余票全部等待 / 预算时限到——收口需人确认 merge-main 时就停在那道门。
为什么自动化执行不会失控 ① 冻结对抗漂移：开工即哈希冻结，之后每次判断都对照冻结值，scope 越界 / 基线漂移自动暴露；② 打回有预算：自动回修最多 2 轮（自修复轮 ≤ 上限 + verify-fails < 2），超限即升级给人——机器不跟死循环较劲；③ 问人单点化：全流程唯一问人通道是 human-decision，主会话统一问、统一路由，子会话永不直接抓人；④ 离场有熔断：预算 80%、心跳双确认、失败不自动重试，代价可控地停下来等人，而不是烧光额度或做出危险动作；⑤ 评审独立性：整需求评审由独立实例做，receipt 哈希链保证任何上游变动都使旧结论失效——不存在「用旧证书放行新代码」。
