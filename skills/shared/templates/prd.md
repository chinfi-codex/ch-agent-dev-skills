# PRD 输出模板

> 本文件是 `/prd` 的输出格式模板，由 agent 在产出文档前读取。
> 修改本文件即时生效，无需重新生成 SKILL.md。
> 产出时必须严格遵循章节结构，不自行增删一级章节。

最终必须输出一份**正式 PRD**。先给状态结论和文档摘要，再输出 PRD 正文。

## 条目化写作约定（产出前必读）

- 功能需求一律条目化：每条需求全局唯一编号 `FR-<模块号>-<序号>`（如 FR-1-1、FR-1-2、FR-2-1），模块内按出现顺序连续编号，全文不重复、不断号。
- 硬性要求（可判定对错的系统行为）一律写成 FR 条目；描述性内容（状态清单、权限矩阵、输入输出字段）保持列表。
- 需求句式按 EARS 规范（中文）：
  - 事件：当 <触发> 时，系统应 <响应>。
  - 状态：当 <前置状态> 持续时，系统应 <行为>。
  - 异常：如果 <异常情况>，则系统应 <处理>。
  - 可选：在 <功能开关 / 版本> 的情况下，系统应 <能力>。
  - 无条件能力（系统应 <能力>）尽量少写，优先转化为前四种。
- FR 粒度：一条 FR 只表达一个可观察行为；「当用户提交时，系统应创建订单并通知用户」类复合行为必须拆成多条 FR。每个「用户操作」步骤至少被一条 FR 覆盖。
- 判定分支、计算口径等写不进单句 EARS 的逻辑，写入模块内「业务规则与处理逻辑」，不压缩进 FR；覆盖这些规则的 FR，其可测试后果必须能验证到这些规则。
- 每条 FR 必须带至少一条**可测试后果**（可验证条件或可度量结果）；写不出可测试后果的条目，降级移入「待确认问题」，不留在正式要求中。
- FR 编号是下游（tech-spec / issue-split / pd-review）的稳定引用锚点：定稿后不复用、不重排；作废条目保留编号并标注「已作废」。
